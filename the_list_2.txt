I went considerably deeper this time: I inspected the actual **v11S source**, its build/test system, the v12R1 diff, the v11S sanitizer run, the fuzz harness, the training example, IR/runtime/compiler/serialization code, and the ownership/API layer. The archive I inspected is the uploaded `3344.zip`.

And there is an important conclusion up front:

> **v11S is a credible development baseline, but it is absolutely not yet a trustworthy training substrate for the v12S you described.**

The existing tests are impressive, but they test a much narrower contract than the one you now want. In fact, the v11S suite printed *“BULLETPROOF”* while I found several classes of bugs that the current suite simply doesn't exercise.

So I would **not** start implementing micromodel functionality yet.

I would first turn v12 into a **correctness + determinism + verification project**, and only then turn on serious training.

For your use case, "training works" is nowhere near enough.

Before v12S is allowed to train a model whose output you intend to trust, this must be true:

```text
                       INPUT

                         ▼
                  ┌──────────────┐
                  │     IR       │
                  │ VALIDATION   │
                  └──────┬───────┘

                  ┌──────────────┐

             │                       │
```

If any of those layers can silently produce a different result, **v12S is not ready**.

The current baseline does pass:

# 3. CRITICAL: cross-graph tensor handles are unsafe

This is probably the first thing I would fix.

Your stable API calls tensors:

```c
typedef void* lancius_tensor_handle;
```

but internally they are simply:

```c
lancius_node *
```

So:

```text
Graph A
 └── tensor A

Graph B
 └── tensor B
```

Nothing prevents:

```c
lancius_add_matmul(graph_B, tensor_A, tensor_B);
```

The API accepts both `void *`.

Then the internal constructor happily accesses the foreign node.

That violates your entire stable-API premise.

### Worse

After:

```c
lancius_graph_destroy_stable(graph);
```

the tensor handle still contains an address.

There is no generation counter.

No registry.

No magic value.

No ownership check.

Nothing.

So:

```c
destroy(graph);

lancius_tensor_element_count(old_tensor);
```

is a use-after-free.

### v12 fix

Don't expose nodes as handles.

Create:

```c
typedef struct {
    uint64_t magic;
    uint32_t generation;
    uint32_t graph_id;
    uint32_t node_id;
    uint32_t flags;
    lancius_node *node;
} lancius_tensor_handle_internal;
```

Likewise for:

```text
context
graph
tensor
model
program
training session
```

Every handle gets:

```text
magic
generation
owner
lifetime
```

Every API entry point validates it.

This is **mandatory before v12S**.

# 4. CRITICAL: the stable API doesn't validate buffer sizes on input

You have:

```c
lancius_bind_data(t, double *data_ptr)
```

but there is no size parameter.

So Lancius cannot establish:

```text
buffer contains exactly N elements
```

It only receives a pointer.

That means this:

```c
double tiny[2];

lancius_bind_data(tensor_1000_elements, tiny);
```

is accepted.

Later the runtime reads 1000 elements.

That is an actual memory-safety contract failure.

### v12 API

You need something like:

```c
lancius_status lancius_tensor_bind(
    lancius_tensor_handle tensor,
    void *data,
    size_t bytes,
    lancius_dtype dtype
);
```

Then validate:

```text
dtype matches
bytes >= required
alignment valid
shape matches
buffer lifetime valid
```

For externally-owned buffers, store:

```text
ptr
bytes
dtype
alignment
ownership = EXTERNAL
```

This becomes part of the runtime state.

# 5. CRITICAL: tensor shapes are not actually validated for Add/Sub/Mul

This is a huge one.

The constructors currently do approximately:

```c
n->shape = a->shape;
n->inputs[0] = a;
n->inputs[1] = b;
```

They don't establish that `b` is compatible.

The comment says:

```text
Allow broadcast
```

but this isn't broadcasting semantics.

The runtime effectively does:

```c
for (k = 0; k < elements; k++)
    output[k] = a[k] + b[k];
```

unless a special INT8 bias path is triggered.

So:

```text
A = [100]
B = [2]
```

can lead to reads beyond B.

### v12 requirement

Implement an actual broadcast engine:

```text
shape_broadcast(a, b)
```

with rules explicitly defined.

For example:

```text
[32,128]
[1,128]
→ [32,128]
```

but:

```text
[32,128]
[64,128]
→ INVALID
```

The compiler should reject this **before runtime**.

# 6. CRITICAL: `reshape()` doesn't verify element conservation

Current code accepts:

```c
lancius_reshape(g, input, ndim, s0, s1, s2, s3)
```

without checking:

```text
product(input_shape) == product(output_shape)
```

That is not a harmless omission.

You can construct:

```text
input = 2 × 4 = 8
output = 3 × 3 = 9
```

and the runtime copies based on the output size.

That's exactly the sort of bug that can corrupt memory or propagate nonsense into training.

### Required invariant

```text
reshape:
    rank <= MAX_RANK
    dimensions valid
    input_elements == output_elements
```

and **zero-sized tensor policy must be explicitly defined**.

# 7. CRITICAL: Permute axes aren't validated

This:

```c
n->shape[0] = dims[a0];
```

assumes:

```text
a0 ∈ [0,3]
```

and that all four axes are unique.

Nothing in the constructor enforces that.

So:

```text
permute(0,0,0,0)
```

is accepted.

And:

```text
permute(0,1,2,8)
```

can read outside `dims`.

### v12

Implement:

```c
bool lancius_validate_permutation(
    uint8_t rank,
    const uint32_t *axes
);
```

Requirements:

```text
0 <= axes[i] < rank
each axis appears exactly once
axes beyond rank are zero/reserved
```

Then test every permutation for ranks 1–4.

# 8. CRITICAL: zero dimensions can reach dangerous math

There are several places where zero dimensions are not properly rejected.

For example:

```c
softmax:
max_val = a[r*C]
```

If:

```text
C = 0
```

that's invalid.

Similarly:

```text
R = 0
```

eventually hits:

```c
total_loss / R
```

in cross entropy.

RMSNorm has:

```c
sq_sum / hidden_size
```

Attention has:

```c
1.0 / sqrt(head_dim)
```

and several other kernels assume nonzero dimensions.

You need a global tensor-shape policy.

I'd recommend:

```text
rank valid
dimensions > 0
element count <= configured maximum
byte count <= configured maximum
```

for v12S unless there is a deliberate need for empty tensors.

Do **not** let individual kernels invent their own policy.

# 9. CRITICAL: stride-zero operations can divide by zero

These are especially important:

```c
conv2d(... stride ...)
maxpool2d(... stride ...)
```

The code eventually calculates:

```c
... / stride
```

but doesn't consistently reject:

```text
stride == 0
```

Likewise:

```text
kernel == 0
```

needs rejection.

This belongs in the graph validator and constructor.

# 10. CRITICAL: GQA has invalid-parameter paths

You calculate:

```c
group_size = n_heads_q / n_heads_kv;
```

So:

```text
n_heads_kv = 0
```

is catastrophic.

And:

```text
n_heads_q < n_heads_kv
```

produces:

```text
group_size = 0
```

and then:

```c
hq / group_size
```

is division by zero.

You also need:

```text
n_heads_q % n_heads_kv == 0
```

unless you explicitly support uneven groups.

This is precisely the sort of invariant your v12 graph validator should own.

# 11. CRITICAL: RoPE assumes an even head dimension

You do:

```c
for (d = 0; d < head_dim; d += 2) {
    q1 = q[idx + 1];
}
```

If `head_dim` is odd, the last iteration accesses the next element.

Therefore:

```text
head_dim % 2 == 0
```

must be an IR invariant.

# 12. CRITICAL: runtime failures can still become "successful" execution

This is one of the biggest architectural problems.

There are many paths like:

```c
if (!a || !b) return;
```

inside execution.

That's dangerous.

Because returning from a kernel isn't necessarily returning an error to the caller.

You can get:

```text
node allocated
↓
input missing
↓
kernel returns
↓
output buffer remains uninitialized
↓
execution continues
↓
loss calculated on garbage
↓
optimizer updates weights
```

That is **the single worst kind of training bug**.

A crash is much safer.

For v12:

> **Every execution path must have a status.**

Change the model from:

```c
void execute_node(...)
```

to something like:

```c
lancius_status execute_node(...)
```

and:

```text
SUCCESS
INVALID_STATE
MISSING_INPUT
OOM
UNSUPPORTED_DTYPE
NUMERICAL_FAILURE
INTERNAL_ERROR
```

Then:

```text
node 483 failed
↓
stop execution
↓
invalidate outputs
↓
propagate exact error
↓
training step aborted
```

Never continue.

# 13. CRITICAL: scheduler detects cycles but returns a partial schedule

Current scheduler:

```c
if (q_tail == 0) {
    fprintf(...);
    break;
}
```

Then it returns `sched`.

That's wrong.

If:

```text
100 nodes
98 processed
cycle detected
```

the caller can receive a schedule containing 98 nodes.

That's not a valid schedule.

It should:

```text
destroy partial schedule
set LANCIUS_ERROR_INVALID_GRAPH
return NULL
```

This is mandatory.

# 14. CRITICAL: scheduler allocation failures aren't handled comprehensively

You have unchecked:

```c
calloc()
malloc()
realloc()
```

in scheduler construction.

For example:

```c
sched = calloc(...)
queue = malloc(...)
waves = malloc(...)
waves = realloc(...)
w->nodes = malloc(...)
```

A failure can turn into NULL dereference or corrupted state.

For a normal application that's bad.

For a training runtime it's unacceptable.

Every allocation needs a failure path.

And **partial construction must be destructible**.

# 15. The scheduler algorithm should be replaced

Current scheduling repeatedly scans the entire graph.

That's effectively:

```text
O(V² + E)
```

in common cases.

Your 10,000-node test passing is nice, but it's not the architecture I'd use for a serious runtime.

Build adjacency lists:

```text
node
 ├── users[]
 └── input_count
```

Then Kahn's algorithm:

```text
queue initial zero-indegree nodes

while queue:
    pop node
    emit node
    for user:
        decrement indegree
        if zero:
            push
```

That's:

```text
O(V + E)
```

and gives you the information you need for:

* scheduling
* liveness
* dependency analysis
* provenance
* invalidation
* backward graph generation

# 16. CRITICAL: `lancius_node_elements()` aborts

You currently have:

```c
abort();
```

for internal tensor-size violations.

I understand why it was introduced.

But for v12S, **do not let library correctness depend on `abort()`**.

There are two distinct cases:

### Internal invariant corruption

Could reasonably be fatal during development.

### User/model/input supplied an invalid shape

Must return:

```text
LANCIUS_ERROR_INVALID_MODEL
```

not kill the host process.

And your verifier itself will be processing potentially malformed external data.

A verifier that terminates the entire host because it encountered malformed data is not a good verifier.

# 17. CRITICAL: `alloc_node()` has several unchecked failures

This is one of the places I'd refactor early.

Currently:

```c
lancius_arena_alloc(node)
```

can fail.

Then:

```c
lancius_ensure_runtime_capacity()
```

can fail.

Then:

```c
lancius_arena_alloc(inputs)
```

can fail.

Then:

```c
track()
```

can `realloc()` fail.

There isn't a coherent transaction.

You can end up with partially initialized nodes.

### v12 design

Make allocation transactional:

```text
validate arguments
      ↓
reserve runtime state
      ↓
allocate node
      ↓
allocate input array
      ↓
initialize everything
      ↓
append to graph
      ↓
commit
```

If anything fails:

```text
rollback
return error
```

No half-node enters the graph.

# 21. Autodiff currently contains mathematically unsafe shortcuts

This needs special attention.

You explicitly did something good:

```text
Transformer backward not implemented
→ fail loudly
```

Keep that philosophy.

But other backward paths are not equally honest.

For example:

```c
MATMUL_BATCHED
```

currently appears to simply pass `grad_out` toward both inputs.

That is not the correct gradient of batched matrix multiplication.

Similarly, broadcast gradient handling is incomplete.

The rule for v12 should be:

> **Every operator is either mathematically verified or explicitly non-differentiable.**

No approximations hiding behind successful execution.

# 22. The autodiff graph needs gradient contracts

For every operator:

```text
forward contract
backward contract
shape contract
dtype contract
numerical contract
```

For example:

### MatMul

```text
A [M,K]
B [K,N]
Y [M,N]

dA = dY @ Bᵀ
dB = Aᵀ @ dY
```

### Broadcast

Forward:

```text
[1,N] → [B,N]
```

Backward:

```text
[B,N] → sum(axis=0) → [1,N]
```

### Batched MatMul

You need:

```text
A [B,M,K]
B [B,K,N]
Y [B,M,N]
```

and corresponding:

```text
dA [B,M,K]
dB [B,K,N]
```

with batch-wise contractions.

These need finite-difference tests.

# 23. Training must have a gradient verification mode


# 25. Optimizer updates need transactional semantics

Do **not** do:


# 27. Deterministic training needs to be a formal runtime mode

You need:

```text
LANCIUS_EXEC_DETERMINISTIC

```

or equivalent.

Deterministic mode means:

```text

```

For your verifier, **deterministic mode should be the default for training/validation**.

# 28. Your current parallel kernels aren't enough for reproducibility

For example, Conv2D weight gradients use:

```text
thread-local gradient
↓
critical
↓
accumulate
```

That's race-safe.

But the accumulation order across threads can still vary.

Floating-point addition is not associative:

```text
(a+b)+c != a+(b+c)
```

So:

```text
thread A result
thread B result
thread C result
```

can produce slightly different final gradients depending on scheduling.

For conventional ML that's often acceptable.

For **your verification system**, it needs to be an explicit policy.

Implement:

```text
deterministic reduction
```

where partials are accumulated in a defined order.

# 30. Serialization needs a major R1/R2 redesign

### Header fields aren't fully validated


# 31. The serializer is not truly endian-independent

The documentation describes fixed-width little-endian encoding.

But the implementation largely writes the packed structs directly.

That works on your little-endian machine.

It isn't the same thing as:

```text
explicit LE serialization
```

v12 should have:

```c
write_u32_le()
write_u64_le()
write_f32_le()
write_f64_le()
read_u32_le()
...
```

throughout.

No raw struct serialization.

---

# 32. Serialization has a serious scalability problem

The CRC implementation reads the entire body:

```text
file
 ↓
malloc(entire body)
 ↓
read entire body
 ↓
CRC
```

For your eventual model/checkpoint sizes, that is unnecessary.

Implement streaming CRC:

```text
read 1 MiB
CRC
read 1 MiB
CRC
...
```

Same for hashes.

Never require:

```text
entire 2 GB model
```

to exist in a temporary buffer just to verify integrity.

---

# 33. The file format needs cryptographic hashing, not only CRC

CRC is good for accidental corruption.

It isn't an authenticity mechanism.

For your provenance system, use:

```text
SHA-256
```

or another cryptographic digest.

The model should have:

```text
architecture_hash
weights_hash
training_config_hash
dataset_hash
```

CRC can remain for fast corruption detection.

Think:

```text
CRC = accidental damage
SHA = identity
```

# 34. There is a concrete model-load correctness bug

The loader handles:

```text
INPUT ndim=4
```

but the general input branch does not correctly reconstruct every supported rank.

In particular, your format supports rank 3, while the loader routes non-4D inputs through the 2D constructor.

That means a serialized 3D tensor can come back with the wrong structural representation.

This must be fixed before serialized training models can be trusted.

# 37. The memory planner needs formal verification

The existing linear-scan planner is clever, but v12 should treat it as a compiler pass whose output must be checked.

For every planned tensor:

```text
offset
size
birth
death
```

verify:

```text
offset + size <= peak
```

and for every overlapping lifetime pair:

```text
ranges do not overlap
```

And importantly:

```text
same storage may overlap ONLY if lifetimes don't overlap
```

Build a debug-only planner verifier:

```c
lancius_memory_plan_validate(plan, schedule, graph)
```

It should brute-force every pair for small graphs.

Then compare the optimized planner against the brute-force verifier.

# 38. Add a reference memory allocator

This is a great redundancy mechanism.

Have two execution modes:

```text
REFERENCE:
each tensor gets independent allocation

OPTIMIZED:
memory planner reuses buffers
```

Run both.

Then:

```text
REFERENCE OUTPUT
       vs

```

must match.

# 41. The bytecode VM is not currently safe enough for v12S

There are several issues.

It assumes:

```text

```

and allocates:

```c
elements = rows * cols
```

without the same checked arithmetic contract as the IR.

It also does:

```c
if (!a) continue;
```

which is exactly the silent-failure behavior we want to eliminate.

And unsupported operations are effectively omitted from bytecode compilation rather than necessarily causing a complete compile failure.

### v12 rule

Compiler:

```text
unsupported operation
→ compilation fails
```

Never:

```text
unsupported operation
→ don't emit it
→ hope output still makes sense
```

# 42. Quantization is not training-safe yet

The quantizer currently:

```text

 ↓

 ↓

```

but retains the original double buffer.

You need explicit semantics:

```text

        │
        ▼
quantized inference weights = INT8
```

During training:

```text
optimizer updates master weights
        │
        ▼
requantize
```

if you're doing quantization-aware training.

Otherwise:

```text
quantized weights
```

should be inference-only.

Do not accidentally make the optimizer update the quantized representation.

# 43. FP32 support needs to be completed consistently

The current v11S path explicitly supports FP32 in certain operations, particularly MatMul.

```text

→ only certain ops
→ otherwise unsupported
```

But v12 must make dtype contracts explicit.

Every operator should have:


and ideally:

```text

```


That's a proper contract.

# 74. The most important distinction for your eventual micromodels

There are going to be **three kinds of correctness**:

### Mathematical correctness

```text
Did the kernel compute the right number?
```

### Runtime correctness

```text
Did Lancius execute the graph without violating memory/state/lifetime rules?
```

### Semantic verification correctness

```text
Did the micromodel correctly classify the external project's state?
```

These must be tested independently.

Otherwise you get a nightmare like:

```text
model says TRUE
```

while the actual problem was:

```text
runtime silently skipped node 481
```

The model may have learned the wrong behavior from a broken runtime.

**That is the fundamental reason I would spend v12R1 and v12R2 almost entirely on infrastructure rather than model features.**

---

And I want to emphasize one thing after actually digging through v11S rather than giving you a generic ML-framework roadmap:

**You are much closer on the numerical side than you are on the trust/contract side.**

The existing MatMul/Conv2D/autodiff work is substantial, and the fact that the current gradient checks and transformer/FP32 known-answer suites pass is a good foundation. But the dangerous problems aren't primarily "your MatMul is wrong." They're things like **invalid graph states being constructible, handles not actually being opaque/lifetime-safe, runtime failures becoming silent returns, incomplete autodiff contracts, and the test harness not exercising those states.**

Those are exactly the bugs that can produce the most terrifying failure mode for your project:

```text
training completes
loss looks reasonable
model looks reasonable
tests pass

                         but

one silent runtime/gradient error
        ↓
training data becomes corrupted
        ↓
model learns corrupted semantics
        ↓
model later becomes the verifier
```

**That is the failure mode v12R1–R3 needs to make structurally difficult or impossible.**

If we get that right, then v12S isn't merely "a version that seems stable enough to train." It becomes a runtime where you can actually make the much stronger statement:

> **"I have evidence that this model was trained by a deterministic, independently tested execution system, from an identified dataset, with verified gradients, verified checkpoints, reproducible execution, and auditable model outputs."**

That is the bar I would use before trusting Lancius with the projects you intend it to watch.
